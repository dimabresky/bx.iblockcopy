# AGENTS.md — разработка модулей 1C‑Bitrix

Этот файл содержит инструкции для AI‑агентов, которые пишут и поддерживают собственный модуль для 1C‑Bitrix.
Всегда следуй этим правилам, если пользователь явно не попросил иное.

## Цель и контекст

- Мы разрабатываем **локальный модуль** для Bitrix Framework (D7).
- Модуль размещается в `local/modules/<vendor>.<module>/`.
- Модуль должен быть:
  - устанавливаемым/удаляемым через админку Bitrix,
  - обновляемым без потери данных,
  - расширяемым через события и публичный API.

## Структура модуля

Соблюдай стандартную структуру модуля Bitrix:

```text
local/modules/<vendor>.<module>/
  .description.php
  .version.php
  include.php
  options.php          (опционально)
  default_options.php  (опционально)

  lib/
    <ClassName>.php    # классы с PSR‑4, неймспейс <Vendor>\<Module>\...

  install/
    index.php
    db/
      <db_type>/
        install.sql    (опционально)
        uninstall.sql  (опционально)
    events/
    admin/
    components/        (если модуль поставляет свои компоненты)
    files/             (доп. файлы, которые копируются при установке)

  lang/
    <lang_id>/
      .description.php
      include.php
      lib/
      install/
```

- В `lib/` размещай все основные классы модуля.
- В `install/index.php` описывай установку/удаление/обновление версии.
- В `events/` — обработчики событий, если они не вынесены в `lib/`.

## PSR и стиль кода

- Следуй **PSR‑12** (стиль), **PSR‑4** (автозагрузка), **PSR‑1** (базовые соглашения).
- Классы модуля:
  - лежат в неймспейсе `<Vendor>\<Module>\...`,
  - файлы в `lib/` соответствуют структуре неймспейса (PSR‑4),
  - один класс/интерфейс/трейт — один файл.
- Именование:
  - классы, интерфейсы, трейты — `PascalCase`,
  - методы — `camelCase`,
  - константы класса — `UPPER_CASE`,
  - поля класса — `camelCase` (если нет других соглашений в проекте).

## SOLID при разработке модуля

### S (Single Responsibility)

- Один класс — одна ответственность:
  - сервисы (например, `OrderSyncService`, `ImportService`),
  - репозитории/шлюзы для работы с таблицами,
  - обработчики событий,
  - API‑контроллеры (если есть свой API).
- Не пиши большую бизнес‑логику в:
  - `include.php`,
  - `install/index.php`,
  - обработчиках событий без выделения сервисов.

### O (Open/Closed)

- Модуль должен быть расширяем:
  - через события Bitrix (`AddEventHandler`, `RegisterModuleDependences`),
  - через публичные сервисы/интерфейсы в `lib/`,
  - через настройки в `options.php`.
- Избегай правок ядра и стандартных модулей; расширяй поведение через:
  - события,
  - собственные точки расширения (хуки, интерфейсы).

### L (Liskov Substitution)

- Если используешь наследование (свои базовые классы или расширение классов Bitrix):
  - не меняй контракт методов,
  - не добавляй неожиданных побочных эффектов в наследниках.
- Реализации интерфейсов должны быть взаимозаменяемы.

### I (Interface Segregation)

- Интерфейсы в модуле делай небольшими и сфокусированными:
  - `OrderReader`, `OrderWriter`, `ProductDataProvider`, `LogWriter` и т. п.
- Не создавай «божественных» интерфейсов с десятком методов.

### D (Dependency Inversion)

- Зависимости внутри модуля строй от абстракций:
  - интерфейсы в `lib/`,
  - внедрение через конструктор или фабричные методы.
- Избегай жёсткой привязки к конкретным классам Bitrix там, где можно использовать абстракции (например, свои репозитории поверх `CatalogProductTable`, `IblockElementTable` и т. д.).

## DRY в модуле

- Избегай дублирования:
  - логики работы с данными (запросы к таблицам, условия, фильтры),
  - обработчиков событий с одинаковой логикой,
  - кода установки/обновления структуры БД.
- Повторяющиеся части выноси в:
  - общие сервисы в `lib/`,
  - базовые классы (например, `BaseRepository`, `BaseEventHandler`),
  - хелпер‑классы (логирование, работа с настройками, кешем).

## Работа с базой данных и ORM

- Предпочитай **ORM Bitrix D7** (`Bitrix\Main\ORM`, `Bitrix\Catalog`, `Bitrix\Iblock` через Data-классы) прямым SQL‑запросам.
- Таблицы модуля:
  - описывай в классах‑сущностях (ORM) или в `install.sql` (если используешь SQL‑подход),
  - при обновлении модуля изменяй структуру через `install/index.php` (метод `doInstall` / `doUninstall` / `upgrade`).
- Все запросы к таблицам модуля централизуй в репозиториях/сервисах, а не размазывай по разным местам.

## События Bitrix

- Для расширения поведения других модулей используй события:
  - регистрируй в `install/index.php` через `RegisterModuleDependences` / `AddEventHandler`,
  - обработчики размещай в `lib/` (отдельные классы) или в `install/events/`, если так принято в проекте.
- Обработчики событий делай тонкими:
  - делегируй основную логику в сервисы модуля,
  - в обработчике только получение данных и вызов сервиса.

## Установка, обновление, удаление

В `install/index.php`:

- Реализуй методы:
  - `doInstall()` — установка модуля,
  - `doUninstall()` — удаление,
  - `upgrade()` / логика обновления версии — миграции структуры БД, данные, настройки.
- При установке:
  - создавай таблицы (через ORM или SQL),
  - регистрируй события,
  - устанавливай настройки по умолчанию (из `default_options.php`),
  - добавляй права доступа (если модуль имеет свою систему прав).
- При удалении:
  - удаляй таблицы (если это явно оговорено),
  - отписывай события,
  - чисти настройки и права.
- При обновлении версии:
  - выполняй миграции БД (добавление полей, индексов, таблиц),
  - обновляй настройки, если нужно,
  - сохраняй данные пользователей.

## Настройки модуля

- Если модуль имеет настройки:
  - используй `options.php` для страницы настроек в админке,
  - выноси логику сохранения/загрузки настроек в отдельный класс (например, `Config`/`Options` в `lib/`),
  - избегай дублирования ключей настроек и логики работы с ними в разных местах.

## Логирование и отладка

- Для логирования используй:
  - `Bitrix\Main\Diag\Log\*` (если проект использует D7‑логгер),
  - или стандартные механизмы (`AddMessage2Log`, свои таблицы логов), если так принято в проекте.
- Не оставляй в коде «отладочных» `var_dump`, `print_r`, `echo` в продуктовой логике.
- Ошибки и важные события логируй структурированно (модуль, действие, контекст).

## Безопасность

- Проверяй права доступа:
  - в админских интерфейсах модуля,
  - в AJAX‑обработчиках,
  - в публичных скриптах, если модуль имеет такие точки входа.
- Экранируй вывод в админке и публичной части (используй `$APPLICATION->ConvertText`, `htmlspecialchars`, и т. п., в зависимости от контекста).
- Валидируй все входные данные (GET/POST/REQUEST) перед использованием в логике и запросах.
- Не пиши в лог чувствительные данные (токены, пароли, персональные данные) без необходимости.

## Git и delivery (feature-bb-pr-flow)

Этот репозиторий — **отдельный git-корень модуля**. Ветки:

| Ветка | Назначение |
|-------|------------|
| `main` | production / стабильный код |
| `dev` | интеграционная ветка |
| `feat/…`, `fix/…` | рабочие ветки от `dev` |

### Обязательный флоу

1. Проверь `git status` и текущую ветку.
2. Убедись, что ветка `dev` существует локально или на remote.
3. `git fetch origin`.
4. Создай feature-ветку от latest `dev` (`feat/<topic>` или `fix/<topic>`).
5. Реализуй только запрошенные изменения.
6. Прогони релевантные проверки.
7. Закоммить на английском по [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).
8. Запусти `/review-bugbot` по изменениям ветки относительно `dev` и auto-fix findings (max **4** итерации на finding). **Не** push и **не** создавай PR, пока этот шаг не завершён.
9. Push ветки и создай PR **только в `dev`** после чистого Bugbot на latest commit (или явного разрешения пользователя по оставшимся findings).
10. Babysit PR: валидные review-комментарии, CI failures этого PR, merge conflicts при ясном intent; иначе спроси пользователя.
11. Когда PR green/mergeable и комментарии закрыты — спроси явное подтверждение перед merge.
12. После подтверждения — merge PR.
13. Удали remote feature-ветку только после успешного merge.

### Правила безопасности флоу

- Никогда не создавай PR, если Bugbot не был запущен после latest commit на feature-ветке.
- Auto-fix Bugbot findings; не превышай 4 fix+re-review итерации на один finding.
- После новых коммитов после Bugbot — перезапусти `/review-bugbot` перед созданием/обновлением PR.
- Не мержи в `dev` при падающем CI, отсутствующих required reviews или unresolved comments.
- Не force-push без явной просьбы пользователя.
- Не удаляй remote-ветку до подтверждения merge.
- Если `dev` отсутствует — остановись и спроси базовую ветку.
- Несвязанные локальные изменения не перезаписывай; спроси, как поступить.

### Bugbot gate

После latest commit и до `git push` / `gh pr create` запусти Bugbot:

```text
Full Repository Path: <absolute repository path>
Diff: branch changes
Base Branch: dev
```

Если findings есть — исправь и перезапусти review (в лимите 4 итераций). Если Bugbot чист — открывай PR в `dev`.
